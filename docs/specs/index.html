MatchFoundry Execution Specs

Phase 11 (Tailwind migration and overlay rules) and Phase 12 (mobile-friendly app). Start here.

How to use these specs

Each step of each phase has its own HTML file. A step file is written so that one session, of any model, can execute it from start to finish without making design decisions. To hand a step to a session, use this prompt:

Read docs/specs/index.html (the "Rules for every executor" section), then execute
docs/specs/phase-11/<step file>.html exactly as written. Do not start any other step.
If the spec does not cover a situation, stop and ask instead of improvising.

11.2 batch files also require reading the conversion guide; each batch file says so.

Rules for every executor

  1. Git. Confirm the current branch with git branch --show-current. If it is not the branch the user named for this work, or main, stop and ask. Never create branches, never commit, never push. Leave all changes uncommitted.
  2. Stay in scope. Edit only the files the step lists. If a fix seems to need a file outside the list, stop and report it instead of editing it.
  3. Frozen shared files. After step 11.0 finishes, these files are frozen for every later step except 11.3 and Phase 12 steps that name them explicitly: src/index.css, src/components/ui/*, src/components/overlay/* (frozen after 11.1), eslint.styles.config.js, playwright.config.ts, e2e/visual/*. If you need a new shared component or token, write the request in your final report and continue without it.
  4. No behavior changes unless the step explicitly asks for one. In Phase 11, a conversion must render the same thing and do the same thing.
  5. Cross-platform. Scripts and npm commands must work in PowerShell and in Bash/Zsh. Normalize paths with .replace(/\\/g, '/') before comparing them. Never hardcode a database port.
  6. Commands. Run the narrowest check that proves the work: npm run typecheck, then npx vitest run <paths>. Run full npm test only where the step says to. Do not run npm run lint across the whole repo.
  7. Visual tests. npm run test:visual is run where the step says. Never run npm run test:visual:update unless the step tells you to; updating baselines is a coordinator decision.
  8. Final report. End with: files changed, commands run with pass/fail, anything skipped and why, any eslint-disable lines added (file, line and reason), requests for shared changes, and visual test results.

Phase 11: Styling foundation and Tailwind migration

Goal: the whole app is styled with Tailwind v4 and shared UI components, with no static inline styles. The app looks the same as before, except for small differences from snapping values onto a token scale. The one behavior change is the new rule for when drawers and pop-ups may be closed.

Wave protocol. Run all five batches of a wave in parallel, in the same working tree. When all five report done:

  1. The coordinator runs npm run typecheck, npm test and npm run test:visual.
  2. The coordinator reviews each failing screenshot diff in test-results/. Token-snap drift (a few pixels of size or spacing change, same structure, same colors) is accepted, and the coordinator runs npm run test:visual:update. Anything else goes back to the batch that owns the file.
  3. The user commits the wave.
  4. Wave 2 starts.

The heaviest batches (F, E, C, A2) are better suited to Claude, and the lighter ones (H, I, D) to agy.

Phase 12: Mobile-friendly app (360×800 and up)

Goal: every page works on a 360×800 phone with no sideways page scroll, tap targets of at least 44px, and readable text. Priority order: spectators navigating from the landing page, then floor judges (match scoring, qualifier entry, review queue), then the compact bracket, then everything else. The work is not done until every route passes.

Decisions already made

TopicDecision
Styling approachTailwind v4 plus a small set of shared components in src/components/ui. Runtime values (tier colors, layout coordinates) are passed as CSS custom properties or inline styles; everything static uses classes.
OrderConvert the whole app to Tailwind first (Phase 11), then make it mobile (Phase 12). The phases run back to back.
Scope of mobileThe entire app. Priority: spectator navigation, then floor judge tools including the review queue, then compact bracket, then everything else.
Dismissal ruleRead-only overlays close on an outside click or tap and on Escape. A form with unsaved changes asks first: “Discard unsaved changes?” with Keep Editing and Discard Changes. An outside click or Escape on that prompt means Keep Editing.
Compact bracketShows seed, name and match wins only (for example 2–1). Brackets never show game scores.
Screenshot testsLight touch: 18 screenshots, mocked API, frozen clock, their own command, never part of npm test or CI.
Spec locationdocs/specs/ in the repo, one HTML file per step.

Definition of done for both phases

  • No file under src/ contains a static inline style; npm run lint enforces this.
  • No legacy global component classes (btn, badge, and the others) remain; src/index.css holds only the theme, base styles and keyframes.
  • Every overlay uses Overlay or ConfirmDialog and follows the dismissal rule.
  • Every route passes the mobile overflow test at 360×800.
  • npm run typecheck, npm test, npm run test:e2e and npm run test:visual all pass.
  • CLAUDE.md, AGENTS.md, docs/UI_ARCHITECTURE.md, docs/TESTING_STRATEGY.md and the product spec describe the new rules.
