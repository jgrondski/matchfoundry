MatchFoundry Execution Specs

Phase 12: mobile-friendly app (360×800 and up), split into steps that run in parallel. Start here.

How to use these specs

Each step has its own HTML file. A step file is written so that one session, of any model, can execute it from start to finish without making design decisions. To hand a step to a session, use this prompt:

Read docs/specs/index.html (the "Rules for every executor" and "Phase 12 conventions"
sections), then execute docs/specs/phase-12/<step file>.html exactly as written.
Do not start any other step. If the spec does not cover a situation, stop and ask
instead of improvising.

The coordinator (the user, or a session the user names) launches the steps of one wave at the same time, waits for all of them, then runs that wave's gate before starting the next wave.

Rules for every executor

  1. Git. Confirm the current branch with git branch --show-current. If it is not the branch the user named for this work, or main, stop and ask. Never create branches, never commit, never push, never stage. Leave all changes uncommitted.
  2. Stay in scope. Edit only the files your step lists. Create only the files your step lists. If a fix seems to need a file outside the list, stop and report it instead of editing it.
  3. Frozen shared files. These files are frozen for every step except the steps that name them explicitly: src/index.css, index.html, src/components/ui/*, src/components/overlay/*, eslint.config.js, playwright.config.ts, package.json, e2e/visual/*, scripts/generateVisualFixtures.ts. If you need a new shared component or token, write the request in your final report and continue without it.
  4. No behavior changes unless the step explicitly asks for one. Desktop (768px and wider) must look exactly as it does today.
  5. Cross-platform. Scripts and npm commands must work in PowerShell and in Bash/Zsh. Normalize paths with .replace(/\\/g, '/') before comparing them. Never hardcode a database port.
  6. Commands. Run the narrowest check that proves the work: npm run typecheck, then npx vitest run <paths>. Do not run full npm test, npm run test:visual or npm run lint across the whole repo; the coordinator runs them at the gate. You may run npx eslint <your files>.
  7. Overflow check. From wave 2 on, each step runs only its own rows of the overflow test: npx playwright test --project=mobile-overflow --grep "\[<step id>\]" (for example --grep "\[12.2a\]"). A failure message lists the elements that stick out past the right edge. Fix every one that is inside your files. If an offending element is in a file another step owns (for example the admin sidebar before 12.1b lands), list it in your report and do not fix it. Never run npm run test:visual or test:visual:update.
  8. Parallel steps share one working tree. npm run typecheck and some Vitest runs cover more than your step, so they can show errors from another step's unfinished file. If every error is in a file outside your step, list each one (file and line) in your report and keep working; never edit another step's file to make it pass. Errors in your own files must be fixed.
  9. Final report. End with: files changed and created, commands run with pass/fail, overflow results for your rows, anything skipped and why, any eslint-disable lines added (file, line and reason), requests for shared changes, and errors seen in other steps' files.

Phase 12 conventions

Goal: every route works on a 360×800 phone with no sideways page scroll, tap targets of at least 44px, and readable text. Priority: spectators navigating from the landing page, then floor judges (match scoring, qualifier entry, review queue), then the compact bracket, then everything else. Read the Styling section of docs/UI_ARCHITECTURE.md first; it governs every class choice.

  • Mobile means below Tailwind's md breakpoint (768px). Phone-only styles use the max-md: variant layered on top of the existing desktop classes. Desktop classes are not rewritten or removed.
  • useIsMobile() (exported from src/components/ui, defined in src/components/ui/useMediaQuery.ts) is used only when the structure differs: a table becomes a card list, or a sidebar becomes a menu. Everything else uses max-md: classes. In unit tests useIsMobile() returns false, so existing desktop assertions stay valid.
  • Targets: a 360×800 viewport has no page-level horizontal scroll; interactive controls in phone layouts are at least 44×44px (min-h-11, min-w-11); body text is at least text-xs; text inputs are max-md:text-base (16px stops iOS from zooming on focus).
  • Numeric inputs (scores, PINs, seeds) get inputMode="numeric". URL inputs get inputMode="url".
  • Wide content that has to stay wide (the organizer sheet, the full bracket views, the round overrides grid) scrolls inside its own overflow-x-auto container, never the page.
  • Sideways-scrolling chip rows use exactly: max-md:-mx-3 max-md:flex-nowrap max-md:overflow-x-auto max-md:px-3 max-md:[scrollbar-width:none] on the row and shrink-0 on each chip.
  • Admin bottom bar clearance. On phones, admin pages have a fixed bottom bar (12.1b) that is 56px plus the safe area. TournamentLayout already pads the content for it. Anything fixed or sticky at the bottom of an admin page uses max-md:bottom-[calc(3.5rem+env(safe-area-inset-bottom))] (plus any gap, for example max-md:bottom-[calc(4.25rem+env(safe-area-inset-bottom))] for a 0.75rem gap) instead of bottom-0, and does not add its own safe-area padding. Overlays (sheets, modals) cover the bar and need nothing.
  • Sticky bars under the admin shell use max-md:top-12 (the admin top bar from 12.1b is 48px tall). Sticky bars under the spectator header also use max-md:top-12 (the spectator header from 12.1a is 48px tall on mobile).
  • Forms: multi-column form grids become one column (max-md:grid-cols-1); side-by-side field rows stack (max-md:flex-col max-md:items-stretch); inputs and selects are max-md:w-full. Page containers use max-md:px-4 max-md:py-4; page titles drop one size step (for example text-3xl gets max-md:text-2xl). Toolbars with several buttons get flex-wrap; a page's primary action is max-md:w-full.
  • Sticky footers inside bottom sheets (Save bars in overlays) use exactly: max-md:sticky max-md:bottom-0 max-md:z-10 max-md:-mx-4 max-md:border-t max-md:border-line max-md:bg-surface max-md:px-4 max-md:py-3, and their buttons get max-md:w-full (stack them with max-md:flex-col). If the overlay's panel padding is not p-4, use the matching negative margin and padding instead of -mx-4/px-4.
  • Card lists (a table that becomes cards on phones):
    1. The card list takes the same row data the table already computes. If that computation is inline in the JSX, first extract it into an exported function in the same file, then use it for both.
    2. The parent renders the card list when useIsMobile() is true and the table otherwise. Search, filter and sort controls above the table stay shared and render in both cases.
    3. The list is <ul className="flex flex-col gap-2">; each item is an <li> holding a Card padding="sm". If a table row is clickable, the whole card is one <button type="button"> doing the same thing. If a row has action buttons, they are IconButtons with plain-word aria-labels in the card's top-right corner (outside the row button).
    4. Values and formatting come from the same helper calls the table cells use; never reimplement them.
    5. Unit tests use renderToStaticMarkup on the card list component directly (not through the parent, which renders the table in tests).
  • Screenshots: desktop screenshots must not change in any Phase 12 step. Mobile screenshots are expected to change; the coordinator reviews and re-baselines them at each gate.

Wave gates (coordinator)

Before launching a wave: start npm run dev in its own terminal and leave it running for the whole wave. Playwright reuses it (reuseExistingServer), so parallel steps don't start and stop competing dev servers.

After every step in the wave has reported:

  1. Read every report. Resolve requests for shared changes and errors reported in other steps' files before continuing.
  2. npm run typecheck and npm test pass.
  3. Overflow: wave 1 runs npx playwright test --project=mobile-overflow --grep "\[12.1a\]|\[12.1c\]"; wave 2 and later run npm run test:overflow (every row).
  4. Wave 1 only: npx playwright test e2e/overlays.spec.ts --project=chromium passes, including the new Back-button tests.
  5. npm run test:e2e passes (golden journeys run at desktop size, where nothing should change).
  6. npm run test:visual: every desktop screenshot passes unchanged. Mobile failures are expected; open each diff in test-results/ and check it matches the wave's intent. With the user's approval, run npm run test:visual:update.
  7. Manual check at 360×800 in Chrome DevTools, using the checklist at the bottom of each step file in the wave.
  8. Hand the working tree to the user to commit and open a PR.

Decisions already made

TopicDecision
Styling approachTailwind v4 plus the shared components in src/components/ui. Runtime values (tier colors, layout coordinates) are passed as CSS custom properties or inline styles; everything static uses classes.
Scope of mobileThe entire app except OBS overlay routes (/:slug/obs/bracket…, /:slug/obs/match/…, /obs/… and any page with ?obs=true), which are fixed-size broadcast surfaces. The OBS hub (/:slug/obs) is in scope.
Phone overlaysModals and drawers become bottom sheets on phones; confirmations stay centered. No swipe-to-dismiss. The browser Back button or back swipe is treated like any other close attempt.
Dismissal ruleRead-only overlays close on an outside click or tap, on Escape and on Back. A form with unsaved changes asks first: “Discard unsaved changes?” with Keep Editing and Discard Changes.
Spectator navigationA bottom tab bar on phones, built from the same items as the desktop header pills.
Admin navigationA 48px top bar showing the tournament name and a Public link, plus a bottom bar with Judge, Quals, Review (with its pending count) and Bracket shortcuts and a Menu button. Menu slides the full sidebar up as a sheet above the bar; tapping Menu again collapses it.
Compact bracketShows seed, name and match wins only (for example 2–1). Brackets never show game scores. Default on public bracket pages on phones; the manage bracket page defaults to the list on phones.
TablesLeaderboard, review queue, standings, roster and player directory become card lists on phones. The organizer sheet stays a matrix and scrolls inside its container.
Screenshot testsMocked API, fixtures generated in code, frozen clock, their own command, never part of npm test or CI. Only the coordinator updates baselines, with the user's approval.

Definition of done for Phase 12

  • Every non-OBS route passes the mobile overflow test at 360×800.
  • Every overlay uses Overlay or ConfirmDialog and follows the dismissal rule, including Back.
  • No file under src/ contains a static inline style; npm run lint enforces this.
  • npm run typecheck, npm test, npm run test:e2e and npm run test:visual all pass.
  • CLAUDE.md, docs/UI_ARCHITECTURE.md, docs/TESTING_STRATEGY.md and the product spec describe the mobile rules.
