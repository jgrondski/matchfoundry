How to use these specs

Each step of each phase has its own HTML file. A step file is written so that one session, of any model, can execute it from start to finish without making design decisions. To hand a step to a session, use this prompt:

Read docs/specs/index.html (the "Rules for every executor" section), then execute
docs/specs/phase-12/<step file>.html exactly as written. Do not start any other step.
If the spec does not cover a situation, stop and ask instead of improvising.

Rules for every executor

  1. Git. Confirm the current branch with git branch --show-current. If it is not the branch the user named for this work, or main, stop and ask. Never create branches, never commit, never push. Leave all changes uncommitted.
  2. Stay in scope. Edit only the files the step lists. If a fix seems to need a file outside the list, stop and report it instead of editing it.
  3. Frozen shared files. These files are frozen for every step except the steps that name them explicitly: src/index.css, src/components/ui/*, src/components/overlay/*, eslint.config.js, playwright.config.ts, e2e/visual/*. If you need a new shared component or token, write the request in your final report and continue without it.
  4. No behavior changes unless the step explicitly asks for one.
  5. Cross-platform. Scripts and npm commands must work in PowerShell and in Bash/Zsh. Normalize paths with .replace(/\\/g, '/') before comparing them. Never hardcode a database port.
  6. Commands. Run the narrowest check that proves the work: npm run typecheck, then npx vitest run <paths>. Run full npm test only where the step says to. Do not run npm run lint across the whole repo.
  7. Visual tests. npm run test:visual is run where the step says. Never run npm run test:visual:update unless the step tells you to; updating baselines is a coordinator decision.
  8. Parallel steps. Steps that run in parallel edit the same working tree at the same time. npm run typecheck and some Vitest runs cover more than your step, so they can show errors from another step's unfinished file. If every error is in a file outside your step, list each one (file and line) in your report and keep working; never edit another step's file to make it pass. Errors in your own files must be fixed. Do not run npm run test:visual while other steps are running; run it once all parallel steps finish.
  9. Final report. End with: files changed, commands run with pass/fail, anything skipped and why, any eslint-disable lines added (file, line and reason), requests for shared changes, and visual test results.

Phase 12: Mobile-friendly app (360×800 and up)

Goal: every page works on a 360×800 phone with no sideways page scroll, tap targets of at least 44px, and readable text. Priority order: spectators navigating from the landing page, then floor judges (match scoring, qualifier entry, review queue), then the compact bracket, then everything else. The work is not done until every route passes.

Qual review workflow

Goal: a qual is its own record that survives having zero scores; saving and verifying are separate; verified quals are locked until unverified; pending quals seed provisional brackets. Run QR.1 then QR.2, both before Phase 12 step 12.2 (12.2 restyles the same review screens).

Definition of done

  • No file under src/ contains a static inline style; npm run lint enforces this.
  • No legacy global component classes (btn, badge, and the others) remain; src/index.css holds only the theme, base styles and keyframes.
  • Every overlay uses Overlay or ConfirmDialog and follows the dismissal rule.
  • Every route passes the mobile overflow test at 360×800.
  • npm run typecheck, npm test, npm run test:e2e and npm run test:visual all pass.
  • CLAUDE.md, AGENTS.md, docs/UI_ARCHITECTURE.md, docs/TESTING_STRATEGY.md and the product spec describe the new rules.
