Step ER.1: Measure every API request

Count database queries and time each API request, return both in a Server-Timing header, and log slow or writing requests, so the 2–3 second write latency can be attributed before and after ER.2–ER.4.

Executor: any model. Prerequisite: none. Run before ER.2 (both edit src/db/index.ts). Read first: index.html “Rules for every executor”, docs/TESTING_STRATEGY.md.

Why

Most writes take 2–3 seconds in production. The code suggests the cause is many sequential database round trips per request (Neon's HTTP driver sends one HTTPS request per query), plus cold starts and Neon waking from scale-to-zero. This step adds the measurement; it changes no behavior.

A. src/server/requestMetrics.ts (new)

import { AsyncLocalStorage } from 'node:async_hooks';

interface RequestMetricsState {
  startedAt: number;
  queryCount: number;
}

const storage = new AsyncLocalStorage<RequestMetricsState>();

/** Runs one API request with its own query counter and clock. */
export function runWithRequestMetrics<T>(fn: () => Promise<T>): Promise<T> {
  return storage.run({ startedAt: performance.now(), queryCount: 0 }, fn);
}

/** Counts one database query against the current request (no-op outside a request). */
export function recordQuery(): void {
  const state = storage.getStore();
  if (state) state.queryCount += 1;
}

export function getRequestMetrics(): { elapsedMs: number; queryCount: number } | null {
  const state = storage.getStore();
  if (!state) return null;
  return { elapsedMs: Math.round(performance.now() - state.startedAt), queryCount: state.queryCount };
}

export function formatServerTiming(metrics: { elapsedMs: number; queryCount: number }): string {
  return `app;dur=${metrics.elapsedMs}, db;desc="${metrics.queryCount} queries"`;
}

/** Drizzle logger that counts queries. Pass as `logger` to every drizzle() call in src/db/index.ts. */
export const queryCounterLogger = {
  logQuery(): void {
    recordQuery();
  },
};

B. src/db/index.ts

  1. Import queryCounterLogger from '../server/requestMetrics'.
  2. Pass logger: queryCounterLogger in the options of both drizzle calls: drizzleNeon(sql, { schema, logger: queryCounterLogger }) and drizzlePg(pgPool, { schema, logger: queryCounterLogger }). Change nothing else. (setDb instances used by tests stay unlogged; that is expected.)

C. src/server/api.ts

  1. Import runWithRequestMetrics, getRequestMetrics, formatServerTiming from './requestMetrics'.
  2. In sendJson, before res.end(...), add: 
    const metrics = getRequestMetrics();
if (metrics) res.setHeader('Server-Timing', formatServerTiming(metrics));
  3. In createApiMiddleware, rename the returned async arrow function's body into an inner function and wrap it: 
    export function createApiMiddleware() {
  const handle = async (req: IncomingMessage, res: ServerResponse, _next?: () => void) => {
    // ...the existing body, unchanged...
  };
  return (req: IncomingMessage, res: ServerResponse, _next?: () => void) =>
    runWithRequestMetrics(async () => {
      try {
        return await handle(req, res, _next);
      } finally {
        logRequestMetrics(req, res);
      }
    });
}
  4. Add this module-level helper next to sendJson: 
    const SLOW_REQUEST_MS = 500;

function logRequestMetrics(req: IncomingMessage, res: ServerResponse): void {
  if (process.env.VITEST) return;
  const metrics = getRequestMetrics();
  if (!metrics) return;
  const method = req.method || 'GET';
  const path = (req.url || '').split('?')[0];
  if (!path.startsWith('/api') && !path.startsWith('api')) return;
  if (method === 'GET' && metrics.elapsedMs < SLOW_REQUEST_MS) return;
  console.log(`[api] ${method} ${path} ${res.statusCode} ${metrics.elapsedMs}ms q=${metrics.queryCount}`);
}

The Vite dev server passes non-API requests through _next(); the path check keeps those out of the log.

D. Tests: src/server/__tests__/requestMetrics.test.ts

  1. getRequestMetrics() returns null outside runWithRequestMetrics, and recordQuery() outside it does not throw.
  2. Inside runWithRequestMetrics, three recordQuery() calls give queryCount === 3; two concurrent runWithRequestMetrics calls (Promise.all, each awaiting a setTimeout(0) between its calls, one recording 1 query and the other 2) keep separate counts.
  3. formatServerTiming({ elapsedMs: 12, queryCount: 4 }) equals 'app;dur=12, db;desc="4 queries"'.
  4. GET /api through createApiMiddleware() (mock request and response as in src/server/__tests__/apiAuth.test.ts, with setHeader recording into a map) sets a Server-Timing header matching /^app;dur=\d+, db;desc="\d+ queries"$/.

How the coordinator reads the numbers (after deploy)

  • Browser DevTools → Network → select a request → Timing tab shows app (total server time) and the query count. Vercel → Project → Logs shows the [api] lines.
  • High q= (20+) and high ms: query pattern. ER.2–ER.4 fix it.
  • Low q= but high ms on the first request after a quiet period: cold start or Neon waking. The keep-warm cron in ER.5 covers event days.
  • Record a baseline for: delete global player, save a match score, save tournament settings, start the qual timer. Compare after ER.4.

Done when

  • Every JSON API response carries a Server-Timing header.
  • Every non-GET request and every GET over 500 ms logs one [api] line with status, duration and query count; tests log nothing.
  • Typecheck and the commands above pass.
